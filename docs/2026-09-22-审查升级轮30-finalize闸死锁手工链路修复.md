# 审查升级轮 30（2026-09-22）：finalize 闸死锁手工链路修复（轮 25 回归）

## 缺口（新审计 #1，我轮 25 引入的回归）

轮 25 给 finalize 加终审闸（缺 `final_review.json` → 409
NOT_REVIEWED），但**全平台只有一个写者**——`run_assemble_phase`。
而平台自己文档化的手工/agent 链路（`/api/video/stitch` 的
next_action 明写：「字幕/混音/归一化后必须调用
/api/review/final-video … verdict=pass 才能 finalize」）**在任何正确
操作下都产生不了这个文件**：`/api/review/final-video`
（api.py:895-902）没有 project_id 参数，`vlm_review_final` 的结果直接
返回、不落盘、不记事件。

后果：不走 run_assemble_phase 的项目（手工 burn/mux/normalize 链、
legacy 端点流、按 AGENT_GUIDE 驱动的 agent 流）——stage 全 PASS、
script 已确认、终验也返回了 pass——**POST finalize 一律 409**，且错误
信息把人引向「重跑 assemble」（可能重新花钱）。修「门被绕过」的同时
把唯一的门开在了唯一一条路上。

## 改动（api.py）

- `FinalVideoReviewRequest` 增加可选 `project_id`；
- `/api/review/final-video`：带 project_id 且 **verdict=pass** 时，把
  终审结论落盘 `final_review.json`（verdict/reason/findings 全量）并记
  `final_review_passed` 事件——手工链路由此获得与 assemble 等效的
  终审凭证；**fix/blocked 不落盘**，finalize 闸的严格性不变；
- 落盘失败（OSError）不改变终验结论本身。

## 测试（TestApiGates，2/96）

- `test_final_video_endpoint_pass_unlocks_finalize`：stub 终审 pass →
  带 project_id 调端点 → final_review.json 落盘 → finalize 200
  RELEASED（手工链路全通）；
- `test_final_video_endpoint_fix_still_blocks`：stub fix → 不落盘 →
  finalize 仍 409（闸未被削弱）。

## 附：轮 30 全量回归中的 E2E 抖动说明

超时 flake 同性质。
