# 审查升级轮 34（2026-09-22）：旧凭证 fail-closed + 端点项目绑定（四审审计）

## 34a：轮 33 哈希 triad 的遗留洞——绕过路径对存量项目复辟

四审审计实证：轮 33 的 triad 有两条放宽，组合起来恰好把"换片再发布"
重新打开：

1. **fr 腿空哈希跳过**：`_fr_sha` 为空（旧 `final_review.json` 没有
   `video_sha256` 字段，或 `vlm_review_final` 读文件 OSError 致
   `_video_sha=""`）时整腿跳过；
2. **pp 腿不是独立见证人**：`/api/video/mux`、`/api/audio/normalize`
   带 project_id 时对**任意 output** 调 `_record_post_production`，
   顺手把 post_production 指纹改写成新文件哈希——换片端点自己把指纹
   改成与新文件自洽。

调用序列：`POST /api/video/mux {video_path: 有缺陷mp4, output_path:
<proj>/final.mp4, project_id}` → `POST finalize` → 200 RELEASED。
截止 deb246d 所有真实项目的凭证都不含 video_sha256（该字段是本轮
刚加的），**绕过面对 100% 存量项目开放**。

**修**：终审凭证缺 `video_sha256` → fail-closed 拦
（`CREDENTIAL_STALE`，detail 指明恢复路径：对当前 final.mp4 重跑
`/api/review/final-video` 或重跑 assemble）。mux/normalize 覆写指纹
的行为不变，但再也不能与旧凭证串通。

## 34b：幂等分支复用主路径同一套比对

轮 32c/33 的幂等分支自己写了一套降格比较（只比 fr 两腿、凭证缺失时
"真空通过"）——已发布项目换片+旧凭证 → 重复 finalize 返回 200 假
确认。**修**：幂等分支改调 `_finalize_artifact_fails`（主路径同一
helper，含 pp 腿、含旧凭证 fail-closed），不一致落到完整门给 409。

## 34c：`/api/review/final-video` 请求级项目绑定

该端点写入发布态凭证却不做项目绑定（中间件只覆盖
`/api/(pipeline|project|variant)/` 与 body 白名单）：持有绑到 A 的
write key 可给任意项目 B 覆写 `final_review.json`（毁证/污染），
`context` 还完全由调用方给（可对着假分镜审出 pass）。
**修**：端点加 `request: Request`，带 project_id 时先过
`_enforce_project_binding` 再落凭证。mux/normalize 的绑定是同类
待办（本轮不扩面）。

## 34d：哈希读取分块化

finalize 原来 `sha256(file.read_bytes())` 全文件进内存（1080p×180s
可达上百 MB，同步端点无超时）。改复用既有 `_file_sha256`（1MB 分块）。
TOCTOU（mux 写一半被读）只会误杀不会误放（fail-closed），维持现状。
