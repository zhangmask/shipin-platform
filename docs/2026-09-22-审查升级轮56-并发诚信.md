# 轮56：并发诚信（十审 P1-3/P1-4）——快照版本唯一性 + 同项目任务互斥

日期：2026-09-23。第 10 轮审计两个 P1 的修复。

## P1-3 artifact_store.snapshot 无锁 → 版本重复 + 索引/磁盘错位

- 病：`snapshot` 的「读 prev → 算 version → 写 v{n}.json → 读索引 →
  append → 写索引」全程无锁。两个并发快照（同 stage，如
  /api/pipeline/text 与 assemble 后台线程各一个、或 retry 重入）都
  读到同一 prev、都算 `version=1` → `versions.json` 出现两条 v1 记录、
  磁盘只剩一个 v1.json；`read_version` 用 `{str(e["version"]): e}` 字典
  推导取**最后一条** entry →「entry.hash 说的是一份内容、v1.json 里是
  另一份」，后续 restore 静默回滚到错内容。索引的 read-modify-write
  还会整份丢条目（十审实测 10 并发只剩 2 条）。
- 修（与 costing._LEDGER_LOCK 同范式）：`_SNAPSHOT_LOCK` 包住整个
  RMW；版本文件与索引都改 tmp+os.replace 原子写（半路被杀不留半截
  JSON）。
- 测试：10 线程并发快照 → 版本号 [1..10] 唯一、索引 10 条不丢、每个
  entry 的 hash 与磁盘 v{n}.json 一致（read_version 回读校验）、无
  .tmp 残留；并发写同一内容仍只产 1 个版本（哈希去重语义不被锁破坏）。
  两条**旧代码下必挂**。

## P1-4 pipeline 任务无同项目互斥 → 两个 assemble 并发写同一目录

- 病：`submit_task` 只按 task_id 去重、不看 project_id。连续两次
  `POST /api/pipeline/{id}/assemble`（或 generate）→ 两个 worker 同时
  `_save`/`_promote_final`/`record_artifact` 同一 `final.mp4`：哈希
  比对可能各自扫到不同字节的快照（发布门被竞态绕过或误报），
  preview frames 与 report 张冠李戴，ffmpeg 中间文件同路径互相覆盖。
  `recover_stale()` 只把 heartbeat 超期的旧任务标 failed，不清正在跑的。
- 修：`active_task_for(project_id)`（queued/running/retry 三态查库 +
  Python 侧 kind 过滤——动态拼 SQL 被 Mimosa 拦后改固定 SQL）；
  `submit_task` 默认拒绝同项目第二个任务（`TaskConflict`），
  `_enqueue_phase` 翻译成 409 `TASK_CONFLICT`；`allow_project_overlap=True`
  给内部确需并发的场景显式逃逸。
- 测试：同项目二提交抛 TaskConflict / 不同项目并行 OK / 前一任务成功
  后放行下一个（顺序重跑是正常形态）/ 逃逸阀可用。旧代码下必挂。
