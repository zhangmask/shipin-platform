# 审查升级轮 43+44（2026-09-22）：账本原子化 / 重入保护 / generate 静默跳镜根除

> 轮 43 来自七审审计的两条原子性问题；轮 44 的四个修复是 E2E **三连挂**
> 的根因链——每一层都是被上层修复暴露的既存 latent bug。

## 43a：成本账本从「静默清零」到「损坏即止」（七审 #5）

`costing` 旧实现三个洞：`record_cost` 读-改-写无锁（异步
`ThreadPoolExecutor` 并发丢行——少计费且两次都真花了钱）；`write_text`
截断式写（磁盘满/进程被杀写在半路留损坏 JSON）；`_load_rows` 损坏时
**静默返回 []**——预算闸判定"没花钱"重新放行，`seq` 从 1 重记，历史
账目无声消失。**账本清零 = 给预算闸开后门。**

修：进程内 `threading.Lock` 包住读-改-写；`mkstemp + os.replace`
原子写；损坏时**备份**（`cost.corrupt-<ts>.json`）并抛
`LedgerCorruptError`。`_enforce_budget` 捕获后返回 422 并指明修复
路径（绝不静默放行）；阶段内熔断 `_budget_exceeded` 对损坏取"停"——
查不了账就不能继续花钱。

## 43b：assemble 重入不再覆盖已发布成片（七审 #6）

旧代码 mux/normalize 直接写 `final.mp4`：已 released 项目重跑
assemble 卡在任一步 → 盘上 final.mp4 变成未归一化甚至截断的中间
产物，而 store 仍 PASS、事件流仍写着"成片已发布"——发布态与盘上
文件脱节且不可回滚。修：全程写 `final.candidate.mp4`，全部成功才
`os.replace` 原子上岗，替换前旧片挪存 `final.published.mp4` 可回滚。
顺带 `_save` 也改原子写（轮 32a 把 record_artifact 挪到 `_save`
之后，半截 JSON 会让"DB 说审过、盘上是坏的"）。

## 44：E2E 三连挂的根因链（四层，逐层被上层修复暴露）

**现象**：轮 43 改动后 E2E 连续三次挂在 assemble→stitch 的
"libx264 Could not open encoder before EOF / no packets"（0.21s 即败）。
三轮回归+两次专项复跑+两份诊断脚本（假生成器秒级复刻 variant 全流程）
后定位——**不是轮 43 的回归，是四个既存 latent bug 的链条**：

1. **generate 静默跳镜（fail-open）**：attempt 循环尾的
   `mrec["qc"] = "fix"` 被 `if r is None: continue` 跳过——三次生成
   全败时带着基准 manifest 深拷贝来的 **stale qc=="ok"** 通过循环后
   检查，generate 假报 ok:True，assemble 拿不存在的基准 clip 拼接才
   炸。修：`generated` 标志，全败显式 `ok:False` 并带错误详情
   （"旧素材/过期 qc 状态不得复用"）。E2E 的 synthetic/coffee 基准
   manifest 都带 qc="ok"，此类场景必踩。
2. **池化 clip 指纹误杀**：轮 42 的 `_clip_input_sha` 用变体**重新
   派生**的 prompt 判新鲜度——style_anchor 覆盖后 prompt 必变，把
   「变体复用基准素材池」这一**设计行为**误判为过期。修：池化 clip
   （文件在他方项目目录）改按**镜头定义指纹** `_clip_shot_sha`
   （shot_id+时长+主体/场景/动作）判定：定义没变 → 池复用合法；
   /rewrite 改镜头定义仍强制重生（七审 #3 的关切不放松）。
3. **链式 last_frame 指向本地不存在的文件**：`chain` 模式写死
   `work/{下一镜}.jpg`，而下一镜首帧是素材池命中（基准路径、本地
   不生成）→ 视频生成 "keyframe image not found"。修：链式末帧跟随
   下一镜的**真实**首帧（含池路径）。
4. **字幕宽度红线只拦不治**：修复 1-3 后 E2E 首次跑完全程真实生成，
   倒在轮 27 的 §10.6 验收门——720p@46px 下 10 字旁白烧出来 63.7%/
   65.4% 超 62% 红线。**门在正确执行**（这就是它存在的意义），正确
   做法是渲染治本：`_build_srt` 新增 `max_line_chars`，长句在最接近
   中点的标点处折两行（渲染器多行 cue 基建早已就绪），assemble 按
   字号/画幅算预算传入。

第五次 E2E（折行修复后）跑满 37 分钟真实生成，失败点已前移至
generate 的 **AGNES 429 Too Many Requests**（连续数小时真实生成的
API 限流，纯外部因素）——且以轮 44 的显式失败正确报出原因，不再
是谜之 stitch 崩溃。第六次复跑（限流窗口内）同样 429 秒败。E2E
的通过依赖 AGNES 视频端点限流窗口，非代码问题；非 E2E 全套 592
绿 + 四个 latent bug 的专项单测（46/46）为代码侧完整证据。
